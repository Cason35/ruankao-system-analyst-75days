# Day 02：系统工程、系统特性与系统思维

日期：2026-08-12  
建议用时：订正热身 20 分钟，授课 70 分钟，例题 20 分钟，作业 45—60 分钟

## 一、今天的学习目标

完成本课后，你应当能够：

1. 从目标、要素、关系、边界、环境、输入、输出和反馈描述一个系统。
2. 说明系统的整体性、目的性、层次性、关联性、动态性和环境适应性。
3. 区分局部优化与整体优化，识别“某个模块更快，但整个业务反而更慢”等问题。
4. 初步理解系统工程的跨专业、全生命周期和权衡优化思想。
5. 面对案例时合理划定系统边界，并找出外部参与者和外部系统接口。

## 二、课前订正：把 Day 01 的薄弱点补上

Day 01 最需要巩固的是“非功能需求”和“约束”的区别。

- 非功能需求描述系统行为要达到的质量水平，如多快、多稳定、多安全、能支撑多少用户。
- 约束限制实现方案的选择，如必须使用已有平台、必须在四个月内上线、数据不得离境。
- 题干没有给出具体质量指标时，可以提出候选指标，但必须注明假设，并由干系人确认。

例如，针对统一会员平台：

- 候选非功能需求：假设高峰期存在 1000 名并发用户，95% 的会员查询请求应在 2 秒内完成。具体并发量和响应时间需根据历史流量及业务期望确认。
- 技术约束：系统必须复用集团现有的统一身份认证平台。
- 项目约束：第一阶段必须在四个月内上线。

再看“不得接受互联网访问”：如果作用于整个统一会员平台，就可能与微信小程序和电商平台发生矛盾。先划清边界后，可以改写为：

> 统一会员平台的管理后台只能通过企业内网访问；互联网用户不得直接访问管理接口。具体网络分区和访问路径需经安全部门确认。

这个例子说明：很多需求问题的根源不是句子写得不漂亮，而是系统边界和适用范围不清楚。

## 三、知识点 1：什么是系统

系统不是一堆元素的简单集合，而是若干相互作用的要素，为实现共同目标而组成的有机整体。

描述一个系统时，可以检查以下内容：

| 观察项 | 要回答的问题 | 开工审批示例 |
|---|---|---|
| 目标 | 系统为什么存在 | 缩短审批时间，防止漏检漏签 |
| 要素 | 系统由什么组成 | 工长、安全员、审批规则、申请数据、软件和服务器 |
| 关系 | 各要素如何相互作用 | 工长提交，安全员依次检查，系统控制状态流转 |
| 边界 | 哪些内容由本系统负责 | 申请、审批、签名、通知和留痕 |
| 环境 | 边界外有哪些影响因素 | 公司制度、施工法规、网络条件和外部认证平台 |
| 输入 | 系统接收什么 | 项目信息、开工材料、检查意见和签名 |
| 输出 | 系统产生什么 | 审批结果、开工许可状态、统计报表和审计记录 |
| 反馈 | 如何根据结果进行调整 | 超时提醒、驳回重提、规则调整和异常整改 |

只列出人员、软件和数据库还不够。系统分析师还需要关注要素之间的关系，以及它们能否共同实现系统目标。

## 四、知识点 2：系统边界与环境

### 1. 什么是系统边界

系统边界用于区分“本系统负责什么”和“本系统外部是什么”。边界之外的人员、组织、设备或其他系统不一定不重要，它们通常通过接口与本系统交互。

划定边界时要回答：

1. 哪些业务活动由本系统直接完成？
2. 哪些活动由人工或其他系统完成？
3. 哪些数据由本系统维护，哪些数据只读取或转发？
4. 本系统能控制什么，不能控制什么？
5. 与外部人员、设备和系统交换什么信息？

### 2. 边界不是界面范围

“某人不登录系统”不代表他一定在系统边界之外；“某个功能显示在页面上”也不代表系统拥有相关数据和规则的最终控制权。

例如，开工审批系统调用统一认证平台完成身份校验：

- 开工审批系统负责发起认证请求、接收认证结果并建立本地会话。
- 统一认证平台负责核验密码或其他凭证。
- 统一认证平台属于外部系统，身份校验结果是双方接口交换的数据。

因此，“用户登录”虽然出现在开工审批系统的页面流程中，但认证能力本身可能在系统边界之外。

### 3. 边界取决于分析目的

边界没有脱离场景的唯一正确答案。

- 分析“开工审批软件”时，人员、规章制度和统一认证平台通常属于外部环境。
- 分析“企业开工管理信息系统”时，人员、流程、数据、软件和制度都可能是系统组成部分。
- 分析“企业安全生产体系”时，开工管理信息系统又只是其中一个子系统。

答题时应先说明分析对象，再给出边界，避免一边把人员当作系统组成要素，一边又在没有解释的情况下把人员全部排除在系统外。

### 4. 用边界表快速作答

| 边界内，由本系统负责 | 边界外，通过接口或流程协作 |
|---|---|
| 创建和校验开工申请 | 统一认证平台完成身份核验 |
| 控制审批状态流转 | 安全员在线下完成现场检查 |
| 保存审批意见和签名记录 | 短信平台实际发送短信 |
| 生成审批进度和统计报表 | 监管部门制定安全规范 |

边界表可以防止两个常见错误：把所有相关事物都塞进系统，或者只写软件页面而忽略外部协作。

## 五、知识点 3：输入—处理—输出—反馈

可以使用 IPOF 模型观察系统：

> 输入（Input）→ 处理（Process）→ 输出（Output）→ 反馈（Feedback）

以开工审批为例：

1. 输入：开工申请、项目资料、检查结果和审批意见。
2. 处理：完整性校验、审批人匹配、顺序流转、权限判断和状态计算。
3. 输出：审批结果、通知、报表和审计记录。
4. 反馈：材料不全则退回；审批超时则提醒；统计发现某类申请频繁驳回后，管理人员改进填报模板或业务规则。

反馈的意义是让系统根据运行结果调整后续行为。没有反馈的流程可能不断重复同一种错误。

反馈可以分为：

- 负反馈：抵消偏差，使系统趋于稳定。例如库存低于安全线就补货，恢复后停止补货。
- 正反馈：强化原有变化，使变化继续扩大。例如使用人数越多，平台内容越丰富，又吸引更多用户。

这里的“正、负”不是“好、坏”，而是表示反馈对原变化的强化或抑制作用。

## 六、知识点 4：系统的基本特性

### 1. 整体性

系统整体功能不是各个部分功能的简单相加。要素之间的组织方式和相互作用会影响整体结果。

例如，申请页面、通知服务和审批页面各自响应都很快，但审批规则把所有申请都发送给同一名安全员，整体审批仍然会拥堵。

### 2. 目的性

系统的设计和运行应服务于明确目标。评价某个模块时，不能只看技术指标，还要看它是否支持整体业务目标。

例如，增加十级审批可能降低漏审风险，却可能违背“将审批周期缩短到四小时”的目标，需要在安全与效率之间权衡。

### 3. 层次性

系统通常由子系统组成，同时又是更大系统的一部分。

```text
企业安全生产体系
└── 开工管理信息系统
    ├── 申请管理子系统
    ├── 审批管理子系统
    ├── 通知服务
    └── 统计与审计子系统
```

分层有助于控制复杂度，但不能忽略子系统之间的接口和共同目标。

### 4. 关联性

系统要素相互依赖，一个局部变化可能通过关系链影响其他部分。

例如，修改施工区域编码，不仅影响申请表单，还可能影响安全员匹配、历史统计、权限规则和外部项目数据接口。

### 5. 动态性

系统状态会随时间、输入和内部活动发生变化。分析时不仅要看静态数据结构，也要看状态如何迁移以及是否存在时间延迟。

例如，一项申请可能经历：

> 草稿 → 待审批 → 审批中 → 已通过或已驳回 → 修改后重新提交

### 6. 环境适应性

开放系统与外部环境交换信息、资源或能量，必须适应政策、市场、组织和技术环境的变化。

例如，安全法规增加新的检查项后，系统的表单、审批规则和报表都可能需要调整。

### 7. 涌现性

系统整体可能呈现单个组成部分不具备的新性质，这称为涌现。

单个安全员只能知道自己审批的申请；当所有审批数据被统一汇集和分析后，整个系统可以识别高风险施工区域、常见驳回原因和异常补签模式。这些风险洞察不是某一条单独记录自身具有的能力。

## 七、知识点 5：系统思维与整体优化

### 1. 从局部因果转向关系网络

线性思维容易认为“一个问题只有一个直接原因”。系统思维则会追问：

- 问题由哪些要素共同造成？
- 要素之间如何相互影响？
- 是否存在反馈回路和时间延迟？
- 当前措施会不会把问题转移到别的部门或未来时点？

例如，为了降低安全员漏审率，管理者要求所有申请都增加两名复核人。短期内复核次数增加，但审批队列变长，人员为了赶进度可能形式化审批，最终未必提高安全性。

### 2. 局部最优不等于整体最优

常见局部优化包括：

- 开发部门为了按期交付，删除审计功能，导致后续合规风险上升。
- 客服为了缩短单次通话时间，快速关闭问题，导致客户重复来电增多。
- 某接口为了减少自身负载采用长时间缓存，导致其他系统一直读取旧数据。

判断优化是否有效，要回到系统整体目标，观察端到端流程和长期结果。

### 3. 权衡而不是追求所有指标同时最大化

性能、安全性、可用性、成本、工期和易用性之间经常存在冲突：

- 更严格的身份校验可能增加操作时间。
- 更高的可用性通常需要冗余资源和更高成本。
- 更快上线可能减少第一阶段功能范围。

系统分析师应明确优先级、说明代价，并让关键干系人参与决策，而不是假设所有目标都能无成本地同时达到最优。

## 八、知识点 6：系统工程

系统工程是为了成功实现复杂系统而采用的跨学科、结构化方法。它关注的不只是软件开发，还包括人员、流程、数据、硬件、网络、制度、运行环境及它们之间的关系。

系统工程具有三个重要视角：

1. 全局视角：从整体目标出发协调各子系统，而不是只优化某个模块。
2. 全生命周期视角：同时考虑规划、开发、部署、运行、维护、演化和退役。
3. 多方案权衡视角：比较不同方案在效果、成本、风险、进度和约束方面的差异。

一个简化的系统工程过程可以表示为：

> 明确问题和目标 → 识别干系人需求 → 划定边界 → 提出候选方案 → 分解与分配需求 → 设计和实现 → 集成 → 验证与确认 → 运行评价与改进

### 验证与确认

- 验证（Verification）：检查系统是否符合已经规定的需求，即“系统是否被正确地构建”。
- 确认（Validation）：检查系统是否真正解决用户和业务问题，即“是否构建了正确的系统”。

例如：

- 测试发现申请列表在 1000 并发下能在 2 秒内打开，属于验证性能需求。
- 上线后审批仍然需要两天，因为安全员没有及时处理通知，说明即使软件符合部分规格，也没有确认实现“缩短审批周期”的业务目标。

## 九、例题讲解

### 例题 1：整体性

某企业分别优化了订单、库存和配送系统，使每个系统的局部处理速度都提高了，但由于三者数据更新周期不同，整体订单交付时间反而变长。这最能说明什么？

A. 子系统性能与整体性能无关  
B. 局部最优不一定产生整体最优  
C. 系统边界越大越好  
D. 所有接口都应改为同步调用

**答案：B。**

解析：各子系统之间存在数据依赖，整体结果取决于要素之间的协同，而不是各项局部指标的简单相加。

### 例题 2：系统边界

会员平台调用第三方短信服务发送验证码。以“会员平台软件”为分析对象时，下列说法正确的是：

A. 短信服务与会员平台有关，所以一定属于系统内部  
B. 短信服务完全不重要，可以不分析  
C. 短信服务属于外部系统，双方通过接口交换请求和结果  
D. 用户收到验证码后，短信服务才成为系统内部组成部分

**答案：C。**

解析：边界外的系统仍可能非常重要，需要分析接口、失败处理、性能和责任边界。

### 例题 3：反馈

系统发现申请超过两小时未审批后自动提醒安全员；若仍未处理，则升级通知项目经理。这主要体现了：

A. 层次分解  
B. 反馈调节  
C. 技术约束  
D. 数据冗余

**答案：B。**

解析：系统根据审批状态和等待时间对后续流程进行调整，属于反馈机制。

### 例题 4：验证与确认

测试团队证明系统全部功能都符合需求规格说明书，但用户仍认为系统无法改善实际工作流程。这说明：

A. 验证和确认都已完成  
B. 验证可能通过，但确认没有通过  
C. 确认通过，但验证没有通过  
D. 需求规格说明书不属于系统分析成果

**答案：B。**

解析：符合规格说明系统“构建得正确”，但没有解决实际问题，说明“构建正确的系统”这一确认目标没有达到。

## 十、案例答题模板：如何描述系统边界

面对系统边界题，可以按四步回答：

1. **声明分析对象：**本题以“××软件系统”为分析对象。
2. **列出边界内职责：**系统直接负责哪些处理、规则和数据。
3. **列出边界外对象：**哪些人员、组织、设备和外部系统与它交互。
4. **描述跨边界接口：**交换什么数据、由谁发起、失败后如何处理。

示例：

> 以开工审批软件为分析对象。边界内包括申请校验、审批流转、状态管理、通知触发和审批留痕；边界外包括工长、安全员、统一认证平台、短信平台和监管制度。工长及安全员通过界面提交数据，系统调用统一认证平台核验身份，向短信平台发送通知请求，并根据外部平台返回结果记录发送状态。现场安全检查本身属于线下业务活动，不由软件直接完成。

## 十一、今天的方法总结

遇到复杂案例时，不要立即拆功能，先完成以下检查：

1. 定目标：系统要改善什么整体结果？
2. 找要素：人员、流程、数据、技术和制度分别有哪些？
3. 划边界：本系统负责什么，外部环境负责什么？
4. 看关系：输入如何经过处理产生输出？有哪些接口和反馈？
5. 防局优：某项措施是否只让一个部门或模块变好，却损害整体目标？
6. 做权衡：效果、成本、进度、安全和可用性之间如何取舍？
7. 双检查：既验证系统符合规格，也确认系统解决真实业务问题。

可以把今天的核心记成：

> 目标决定边界，关系决定整体，反馈推动调整，权衡实现优化。
